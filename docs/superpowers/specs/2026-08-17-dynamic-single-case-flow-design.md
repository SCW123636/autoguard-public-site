# AutoGuard 动态单案例完整归因展示设计

## 1. 目标

在保留 `enterprise-output-v1` 单案例展示结构的基础上，增加一个动态案例入口。用户从企业提供的十个脱敏真实案例中选择任意一个后，页面加载该案例对应的数据，并用同一套完整的 G1-G7 归因链进行讲解。

本次目标是证明：

```text
案例输入 -> 真实数据读取 -> 方法判断 -> 证据门禁 -> 企业下一步动作
```

不是重新设计一个摘要仪表盘，也不是根据一段文本自动编造完整归因。

## 2. 已确认边界

- 单个案例的展示方式以原参考版本为准。
- 十个真实脱敏案例共用一个展示模板。
- 动态内容必须来自当前案例数据，不能读取预设的展示结论。
- 企业问题、真实数据、派生观察、缺失项和方法结论必须分开。
- 缺失证据显示为“当前数据未提供”，不能由 AI 或默认值补齐。
- AI 只整理证据并形成受限候选，不确认根因、责任域或 OTA 因果。
- 人工审核是企业动作门禁，审核人数和组织规则由企业决定。
- 第一版动态入口只选择企业已提供的十个真实案例，不接受任意自然语言直接生成证据链。
- 不在主体展示中加入无关的工作台总览、二级查询、车端运算说明或额外运营信息。

## 3. 用户流程

### 3.1 案例入口

页面首屏提供一个清晰的“选择企业案例”入口。选项至少包含：

- 案例编号
- 功能域
- 企业问题标题

选择案例后，不进入新的摘要页，而是直接进入该案例的完整展示页。

### 3.2 单案例开场

开场保持参考版本的结构，动态填充：

- 案例编号和数据标签
- 企业问题原文
- 本案需要回答的排查目标
- 当前处理状态

企业问题原文是企业报告，不得被展示成已经验证的事实。

### 3.3 G1-G7 阶段导航

保持参考版本的阶段导航和“一次聚焦一个阶段”的阅读方式：

1. G1 问题定义
2. G2 证据冻结
3. G3 受限候选与因果门禁
4. G4 企业人工审核
5. G5 验证协议
6. G6 工程验证结果
7. G7 修复关闭与知识沉淀

每个阶段展示四类信息：

- 企业问题：企业在该阶段需要回答什么
- 真实数据发现：当前案例数据实际支持什么
- 我们的方式：AutoGuard 采取了什么处理方法
- 下一步门禁：允许继续、补证、停答或转人工审核到哪里

### 3.4 案例收束

页面底部保留参考版本的收束区：

- 企业最终得到什么
- 当前证据链覆盖到哪里
- 当前允许的工程动作
- 当前永久边界

收束区必须反映当前案例的动态结果，不显示十个案例的混合摘要。

## 4. 数据与运行时设计

### 4.1 输入数据模型

案例对象至少包含：

- `case_id`
- `title`
- `domain`
- `enterprise.problem`
- `enterprise.goal`
- `enterprise.status`
- `engineering.evidence_snapshot_id`
- `engineering.evidence_items`
- `engineering.derived_observations`
- `engineering.hypotheses`
- `engineering.missing_evidence_ids`
- `engineering.validation_protocol`
- `engineering.engineering_result`
- `engineering.closure`
- `safety_route`
- `evidence_tension_state`

### 4.2 动态适配层

新增一个案例适配层，将当前案例转换为参考展示所需的 G1-G7 视图：

```text
RealCase
  -> buildCaseOpening()
  -> buildStageViews()
  -> evaluateEvidenceGate()
  -> buildCloseout()
  -> ReferenceCaseFlow
```

展示组件不得直接读取另一个案例的内容，也不得通过案例编号硬编码整页结论。

### 4.3 证据门禁

运行当前案例时至少执行：

1. 校验案例身份、问题描述和证据快照是否存在。
2. 收集当前快照中的 Evidence ID。
3. 校验候选的支持、反证和缺失引用是否属于当前快照或已登记缺失项。
4. 判断是否存在证据张力。
5. 判断是否存在安全优先升级条件。
6. 判断是否形成受限候选。
7. 生成对应的 G4 人工审核门禁。
8. 继续填充 G5-G7，缺失处明确停答或显示“当前数据未提供”。

决策优先级：

```text
无效 Evidence ID
  > 安全优先升级
  > 证据张力停答
  > 受限候选进入人工审核
  > 证据不足终止归因
```

所有路径均禁止根因确认和 OTA 因果确认。

## 5. 展示结构

页面只保留一条清晰主线：

```text
选择案例
  ↓
企业提出的问题
  ↓
G1-G7 单阶段讲解
  ↓
证据和门禁结果
  ↓
企业最终得到什么
```

不新增以下内容：

- 单独的首页摘要仪表盘
- 与案例无关的十案统计图
- 额外的二级查询工作台
- 与核心方法无关的架构说明
- “车端不进行运算”等非核心展示信息

## 6. 错误与缺失处理

- 未选择案例：显示选择提示，不渲染空白归因链。
- 案例字段缺失：对应字段显示“当前数据未提供”。
- Evidence ID 无效：G2 阻断，G3 不输出候选，G4 转人工处理。
- 存在证据张力：同时保留支持和反证，输出停答。
- 涉及高后果安全风险：先输出安全升级，技术归因停答。
- 候选证据不足：只能显示补证或终止自动归因。
- G5-G7 缺少工程数据：显示不可验证原因，不使用外部案例补齐。

## 7. 验收标准

### 功能

- 十个企业真实案例均可被选择。
- 任意选择一个案例后，案例编号、问题、证据、候选、缺失项和 G1-G7 内容全部随案例变化。
- 单案例展示结构与参考版本一致：开场、阶段导航、阶段详情、翻页和收束区均存在。
- 同一案例重复运行得到相同门禁结果。
- 修改当前案例数据后，相关展示和门禁结果随之变化，不能继续使用旧案例结论。

### 方法边界

- 支持、反证、缺失证据均可回溯到当前案例。
- 无效 Evidence ID 会阻断分析。
- 证据张力不会被自动裁决。
- 安全风险会优先升级。
- 不允许输出已确认根因、责任域或 OTA 因果。

### 视觉与可用性

- 首屏先让用户看懂“选择案例后查看完整归因链”。
- 单案例内容按阶段阅读，不堆叠全部细节。
- 桌面端和移动端无横向溢出、文字重叠或阶段卡片挤压。
- 关键状态、门禁和下一步动作清晰可见。

### 验证

- 运行时脚本语法检查通过。
- 十个案例动态映射测试通过。
- 至少覆盖受限候选、证据张力、安全升级和证据不足四条分流。
- 浏览器控制台无错误。
- 发布后的公开地址可以现场完成“选择案例 -> 查看完整案例 -> 切换阶段”。

## 8. 实现建议

推荐在当前代码上做定向调整：

1. 恢复或重建参考版本的单案例流组件。
2. 将当前十个真实案例作为唯一数据源。
3. 保留 `demo-engine.js` 作为纯门禁计算层，但扩展为输出 G1-G7 视图所需的动态结构。
4. 使用 `presentation.js` 负责把单案例数据映射为阶段讲解内容。
5. 将动态入口放在单案例流顶部或开场前，不改变单案例阅读主体。
6. 通过测试锁定“任意十案可切换、内容随案例变化、门禁结果不写死”。
